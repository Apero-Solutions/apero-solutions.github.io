Diagnostics and Error Codes

Every reading ModBridge Pro publishes carries its own verdict. When a register does not read, the payload says why — this is the primary diagnostic channel for a device in the field with no serial console attached.

Where the codes appear

Destination

How a failure looks

MQTT

"CommQuality": "BAD" on that register, plus err (numeric) and errText (name), e.g. "err": 224, "errText": "TIMEOUT".

Google Sheets — tabular

The register’s cell reads Error: TIMEOUT instead of a value.

Google Sheets — JSON

The cell holds the full payload, including the err / errText fields.

A failed register still appears in every message with a value of 0, so downstream systems see a complete, consistently-shaped record. Always test CommQuality before trusting a value.

Error code reference

Exception codes — the device answered and refused

The field device is alive, addressed correctly and talking. It is the request it does not like, which almost always means the register list needs correcting rather than the wiring.

Transport failures — nothing usable came back

Raised locally, because the exchange itself failed. These point at the physical layer, the serial settings, or the network.

Name

Usual cause

0xE0

TIMEOUT

No answer at all. The most common error by far: wrong Device ID, wrong baud rate or parity, A/B swapped, or the device unpowered.

INVALID_SERVER

The configured Device ID is out of the valid 1–247 range.

PARAMETER_COUNT_ERROR, PARAMETER_LIMIT_ERROR

Internal request-building faults; report these with your register list.

0xE8

REQUEST_QUEUE_FULL

Requests are being issued faster than the bus can carry them. Lengthen the Update Interval.

233

0xE9

ILLEGAL_IP_OR_PORT

Modbus TCP: the server IP or port in the configuration is not valid.

234

0xEA

IP_CONNECTION_FAILED

235

ADDR_UNMAPPED

Nothing was ever sent. The configured address falls outside every Modbus space — see Register address ranges. Fix the address; the bus is not involved.

Working through a silent device

When a device reads nothing at all, work down this list in order — each step rules out a whole class of cause:

  1. Check the error code first. ADDR_UNMAPPED is a configuration typo and no amount of wiring work will fix it. TIMEOUT and ILLEGAL_DATA_ADDRESS point in opposite directions: the first means nothing answered, the second means the device answered and is telling you the address is wrong.

  2. Does the RX LED pulse at all? A pulse means at least one register on some device is reading, which proves the bus, the serial settings and the transceiver. No pulse at all points at the bus itself.

  3. Confirm the serial settings. Baud rate and parity must match every device on the bus. A device set to 8E1 against a gateway on 8N1 is silent, exactly like a broken wire.

  4. Confirm the Device ID. It is the ID configured on the field device, not its position in the list. SERVER_ID_MISMATCH means two devices share one ID.

  5. Check A/B polarity and termination. Reversed A/B is silent; missing termination on a long run shows up as intermittent CRC_ERROR. Terminate with 120 Ω at each end for runs over ~10 m.

  6. Check the address convention. If values arrive but are wrong, suspect an off-by-one before suspecting the device — a shifted read returns the neighbouring register’s perfectly plausible value.

  7. Check the byte order. Absurd FLOAT32 values (1e-38, 4.7e24) mean the word order is wrong: try CDAB.

Interpreting a partly-working device

Symptom

Likely cause

Some registers good, others ILLEGAL_DATA_ADDRESS

Those addresses are not implemented on the device. The gateway has already retried them individually, so the verdict is per-register and reliable.

All registers on one device time out, others fine

That device alone: its ID, its power, or its drop cable.

Everything times out intermittently

Bus contention, marginal termination, or a device too slow at the configured interval. Lengthen the Update Interval first.

A register sits at 0 and never moves

Check CommQuality for that register before assuming the process value really is zero — a failed read publishes 0 too, and the two are indistinguishable without it.
