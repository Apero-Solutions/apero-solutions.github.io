.. _configuration:

=======================
Configuration Reference
=======================

All settings are configured through the browser-based web interface.  Open
``http://192.168.4.1`` (Wi-Fi) or ``http://192.168.5.1`` (Ethernet) when in
configuration (AP) mode, or the device's assigned IP address once it is
connected to your network.

The interface is divided into six tabs, described below.


Internet Connection Tab
========================

Defines how ModBridge Pro reaches the internet to publish data.

.. list-table::
   :widths: 25 25 50
   :header-rows: 1

   * - Setting
     - Options
     - Notes
   * - Connection Type
     - Wi-Fi / Ethernet
     - Wi-Fi is recommended for most installations.
   * - Wi-Fi SSID
     - Text or scan list
     - Click **Scan Networks** for auto-detection.  Currently connected
       SSID is highlighted.
   * - Wi-Fi Password
     - Text
     - Stored encrypted.  Toggle visibility with the eye icon.
   * - Ethernet IP Mode
     - DHCP / Static
     - Static mode requires IP address, Subnet Mask, Gateway, and DNS.

.. note::

   When **Modbus TCP** is selected in Protocol Settings, the Ethernet port
   is dedicated to Modbus communication and **cannot** simultaneously serve
   as the internet uplink.  Use Wi-Fi as the internet connection in that
   scenario — the device aborts startup if Ethernet is selected for both.

If the link drops while running, the device retries every 30 seconds: Wi-Fi
by re-issuing a connect, Ethernet by waiting for the link and an IP to come
back.  Modbus polling and buffering continue throughout.


Protocol Settings Tab
======================

Defines how ModBridge Pro communicates with your Modbus field devices.

Modbus RTU (RS-485)
-------------------

.. list-table::
   :widths: 25 35 40
   :header-rows: 1

   * - Setting
     - Options
     - Notes
   * - Baud Rate
     - 9600 / 19200 / 38400 / 57600 / 115200 bps
     - Must match every slave on the bus.
   * - Data Bits
     - 8 / 7
     - Virtually always 8.
   * - Parity
     - None / Even / Odd
     - Must match slave configuration.
   * - Stop Bits
     - 1 / 2
     - Typically 1 when parity is enabled; 2 when parity is None.

.. warning::

   Parity is the most commonly mismatched setting on a new bus.  A device
   set to 8E1 while the gateway is set to 8N1 answers nothing at all, which
   looks identical to bad wiring — see :ref:`diagnostics`.

Modbus TCP (Ethernet)
---------------------

.. list-table::
   :widths: 25 75
   :header-rows: 1

   * - Setting
     - Notes
   * - Server IP
     - IPv4 address of the Modbus TCP server (e.g., a PLC or another
       gateway).
   * - Server Port
     - Standard is **502**.  Change only if the server uses a non-standard
       port.
   * - Device Ethernet IP
     - Static IP assigned to ModBridge Pro's Ethernet interface in TCP
       mode.  Must be on the same subnet as the server.


Modbus Devices Tab
==================

Define each Modbus slave device and the registers you want to read.  Up to
**5 devices** and **50 registers per device** are supported.

Registers can be typed in one row at a time, copied from a device already
configured on the page, or loaded from a previously exported file — see
`Entering registers faster`_.

Per-device parameters
---------------------

.. list-table::
   :widths: 20 20 60
   :header-rows: 1

   * - Parameter
     - Range
     - Description
   * - Device ID
     - 1–247
     - The Modbus slave address configured on the field device.  It is also
       what identifies the device in the published payload (``slaveId``).
   * - Slave Name
     - Text, up to 29 characters
     - Optional.  A naming helper, **not a stored setting** — pressing
       **Apply** rewrites this device's register names in the table below as
       ``SlaveName_RegisterName``.  See `Naming a device`_.

.. _naming_a_device:

Naming a device
---------------

Several identical meters on one bus produce identical register names, which is
hard to read in an MQTT payload and impossible to read in a tabular Google
Sheet — the data cells there carry no names at all, only positions, so three
chained meters give three indistinguishable ``Voltage_L1`` columns.

Typing a **Slave Name** and pressing **Apply** prefixes every register name on
that device:

.. list-table::
   :widths: 50 50
   :header-rows: 1

   * - Before Apply
     - After Apply with ``Chiller1``
   * - ``Voltage_L1``
     - ``Chiller1_Voltage_L1``
   * - ``Power_Total``
     - ``Chiller1_Power_Total``

The prefix is written straight into the register names, which is all the device
ever stores — there is no separate name field in the configuration.  What you
see in the register table is exactly what gets saved, and it flows through to
the MQTT ``rName`` field and the Google Sheets column headings with no further
setup.

.. important::

   The **31-character register-name limit covers the combined result**, so the
   Slave Name eats into the budget for each register name.  A 9-character name
   such as ``Chiller_1`` leaves 21 characters per register.

   The hint under the Slave Name box shows how much room is left as you type,
   and Apply refuses outright — changing nothing — if any register would go
   over.  It never shortens a name silently, because a truncated name would
   still be published and would be very hard to spot afterwards.

Working with the prefix:

* Pressing **Apply** a second time **replaces** the prefix rather than adding
  another one, so a device can be renamed freely.
* Clearing the box and pressing **Apply** removes the prefix — that is the undo.
* Registers added afterwards are picked up by the next **Apply**; rows that
  already carry the prefix are not doubled.
* When a saved configuration is loaded, the name is recovered from the register
  names if all of them share one, so renaming after a reboot works normally.
  A device whose registers happen to share a lead — ``Voltage_L1``,
  ``Voltage_L2`` — may show ``Voltage`` in the box; nothing changes unless you
  press Apply.

Per-register parameters
-----------------------

.. list-table::
   :widths: 20 30 50
   :header-rows: 1

   * - Parameter
     - Options / Range
     - Description
   * - Variable Name
     - Text, up to 31 characters
     - Becomes the ``rName`` field in the MQTT payload and the column
       heading in a tabular Google Sheet.  Use short, meaningful names
       (e.g., ``voltage_L1``, ``active_power``).  A device prefix shares
       this 31-character budget — see `Naming a device`_.
   * - Data Type
     - Boolean, INT16, UINT16, INT32, UINT32, FLOAT32
     - See :ref:`data_types`.
   * - Register Address
     - 5-digit Modbus reference
     - See `Register address ranges`_ below.
   * - Byte Order
     - ABCD / CDAB / BADC / DCBA
     - Adjust for endianness differences.  Consult the device's Modbus
       register map.

.. _entering_registers_faster:

Entering registers faster
-------------------------

Typing 50 rows by hand for each of several identical meters is slow and
error-prone.  Two shortcuts on this tab avoid it.

**Duplicate** — each device card has a *Duplicate* button in its header.  It
creates a new device carrying a copy of every register on the original and
pre-fills the Device ID with the lowest free address at or above the source's
own, so a chain of identical meters is built by pressing it repeatedly.  Only
the Device ID normally needs changing afterwards.

If the source device has a Slave Name, the copy takes the next free one —
``Chiller1`` becomes ``Chiller2`` — and its register names are rewritten to
match, so the two devices never publish under identical names.  See
`Naming a device`_.

**Import / Export** — the buttons at the top of the tab move a whole register
map between units, described next.

.. _register_map_files:

Importing and exporting a register map
--------------------------------------

**Export register map** downloads the devices, their registers, and the
Modbus link settings (protocol, baud rate, data bits, parity, stop bits, and
the TCP server address) as a JSON file named
``modbridge-registers-YYYYMMDD-HHMM.json``.

.. important::

   The export contains **no credentials** — no Wi-Fi password, no MQTT
   password, no Google Sheets key.  It is a register map, not a device
   backup, and is safe to email to a site engineer or keep in a project
   folder.  There is no way to restore a device's secrets from it; those
   must be re-entered on the unit.

**Import register map** reads such a file back.  Because it replaces every
device currently shown on the page, it asks for confirmation first, and asks
again separately before applying the Modbus link settings — so a map can be
loaded onto a bus that runs at a different baud rate without disturbing it.

.. note::

   Importing only fills in the form.  Nothing reaches the device until you
   press **Save Configuration**, so there is always an opportunity to review
   and adjust the imported map — in particular the Device IDs, which are
   rarely identical between two sites.

A file holding more than 5 devices or more than 50 registers on a device is
truncated to the supported limits, and registers whose address is missing or
out of range are dropped.  Anything adjusted this way is listed in the status
line under the buttons rather than applied silently.

The format is plain JSON and easy to generate elsewhere — useful for building
a register map for a meter model once and reusing it across installations:

.. code-block:: json

   {
     "type": "modbridge-register-map",
     "version": 1,
     "modbus": { "protocol": "rtu", "baudrate": "9600", "parity": "N" },
     "slaves": [
       {
         "address": 1,
         "registers": [
           { "name": "Voltage_L1", "address": 30001,
             "dataType": "UINT16", "byteSwap": "NO_SWAP" }
         ]
       }
     ]
   }

A file containing only the ``slaves`` array — or a bare array of devices — is
also accepted.

Device ID checks
----------------

Two devices answering to the same address collide on every poll, and the
duplicate button makes that easy to do by accident.  A Device ID entered
twice is highlighted as you type, and **Save Configuration** is refused with
a message naming the address and the two devices using it.

Saving is also refused when a device has no Device ID, has one outside
1–247, or has no register with both a name and an address filled in.  In each
case the page switches to this tab and focuses the field at fault.

.. _register_addressing:

Register address ranges
-----------------------

Addresses are entered in the **5-digit Modbus reference notation** used by
most device manuals.  The leading digit selects the register space and the
rest is a **1-based** position within it:

.. list-table::
   :widths: 20 20 60
   :header-rows: 1

   * - Address range
     - Register type
     - Typical content
   * - 00001–09999
     - Coils (function 01)
     - Digital outputs, relay states
   * - 10001–19999
     - Discrete Inputs (function 02)
     - Digital inputs, alarm flags
   * - 30001–39999
     - Input Registers (function 04)
     - Measured values (voltage, current, temperature)
   * - 40001–49999
     - Holding Registers (function 03)
     - Setpoints, configuration parameters

.. warning::

   **Manuals that print a 0-based offset need +1.**  A meter whose manual
   lists "voltage at 0, current at 2" against a 3xxxx input-register map is
   describing offsets, so those are entered here as ``30001`` and ``30003``.
   A manual that already prints ``30001`` is using the same convention as
   this field and needs no adjustment.  An off-by-one usually reads a
   plausible but wrong value rather than failing outright, so check it
   before trusting the numbers.

   Addresses in ``20001–29999``, above ``49999``, or exactly on a boundary
   (``0``, ``10000``, ``30000``, ``40000``) belong to no space.  The web
   form accepts them, but they are never put on the wire and every reading
   is reported as ``ADDR_UNMAPPED``.

.. _data_types:

Data Types
----------

.. list-table::
   :widths: 15 10 30 45
   :header-rows: 1

   * - Type
     - Registers
     - Value Range
     - Typical Use
   * - BOOL
     - 1 bit
     - 0 or 1
     - On/Off states, relay outputs, alarm flags
   * - INT16
     - 1
     - −32 768 to 32 767
     - Signed temperature, current, status
   * - UINT16
     - 1
     - 0 to 65 535
     - Unsigned counters, percentages, raw ADC
   * - INT32
     - 2
     - −2 147 483 648 to 2 147 483 647
     - Energy accumulators, pulse counters
   * - UINT32
     - 2
     - 0 to 4 294 967 295
     - High-range counters, uptime, flow totals
   * - FLOAT32
     - 2
     - IEEE 754 single precision
     - Voltage, power, frequency, temperature with decimals

A 32-bit type consumes the addressed register **and the one after it**, so
plan the address list accordingly.  In a coil or discrete-input space every
type reads as a single bit regardless of what is selected.  FLOAT32 values
are published with 6 decimal places.

Byte Swap Modes
---------------

Some devices store 32-bit values with a non-standard byte/word order.
The four modes cover all common conventions — the letters describe where
the source bytes A, B, C, D end up:

.. list-table::
   :widths: 25 75
   :header-rows: 1

   * - Mode
     - When to use
   * - No Swap (ABCD)
     - Big-endian devices (most common; try this first).
   * - Word Swap (CDAB)
     - Little-endian 32-bit values stored as two swapped 16-bit words.
   * - Byte Swap (BADC)
     - Bytes within each word are reversed.
   * - Word+Byte (DCBA)
     - Both word and byte order reversed (fully little-endian).

A wrong byte order on a FLOAT32 typically shows up as a wildly implausible
number (``1e-38``, ``4.7e24``) rather than a small error.

How registers are read
----------------------

Registers are not fetched one at a time.  Before each poll the gateway maps
every configured register onto its wire address, sorts them, and merges
neighbours into as few requests as possible:

* Up to **100 registers** (or **800 bits**) per request.
* Gaps of up to **8 registers** (or **16 bits**) between wanted addresses
  are read across rather than split into a second request — one extra round
  trip costs far more than a few discarded values.
* Each register space is requested separately, since each uses its own
  function code.

The practical consequence is that a tidy, contiguous address list polls
dramatically faster than the same number of registers scattered across the
map.  If one block fails, only the registers in that block are marked bad;
the rest of the cycle still publishes.

When a device *answers* but rejects a block — an exception such as
``ILLEGAL_DATA_ADDRESS``, typically because the merged range crossed into
registers the device does not implement — the gateway automatically re-reads
that block's registers one at a time, so the valid ones still come back.
Transport failures (a timeout, a CRC error) are not retried that way: the
device is not talking at all, and N more timeouts would stall the whole poll
cycle.


IoT Publishing Tab
==================

Selects the cloud destination and how often data is sent.  Covered in full
in :ref:`iot`.

The **Update Interval** dropdown (1 s, 5 s, 10 s, 30 s, 1 min, 5 min,
15 min) sets one cadence for the whole device: each interval triggers one
Modbus poll cycle and one publish.


Firmware Update Tab
===================

Shows the running firmware version and accepts an update bundle.  See
:ref:`ota`.


Summary Tab
============

The *Summary* tab displays a read-only overview of the current configuration
before you click **Save Configuration**.  Verify the settings here before
committing to ensure no typos in register addresses or server IPs.

Saving writes ``/config.json`` to the device's internal filesystem and
reboots after about 3 seconds.  Secrets in that file are encrypted — see
:ref:`security`.
