.. _overview:

========
Overview
========

What is ModBridge Pro?
======================

ModBridge Pro B15 is a compact, industrial-grade **IoT gateway** that continuously
reads data from legacy **Modbus** field devices — energy meters, temperature
controllers, PLCs, sensors — and forwards that data to modern cloud platforms
such as **MQTT brokers** or **Google Sheets**, without requiring any changes
to the existing field devices.

Key capabilities
----------------

.. list-table::
   :widths: 30 70
   :header-rows: 0

   * - **Modbus polling**
     - Reads up to 5 Modbus slave devices with up to 50 registers each,
       over RS-485 serial (RTU) or Ethernet (TCP).  Registers that sit close
       together are fetched in a single request rather than one at a time.
   * - **Dual connectivity**
     - Connect to the internet via Wi-Fi or wired Ethernet.
   * - **Cloud publishing**
     - Push data to any MQTT broker or directly to Google Sheets, in JSON
       or tabular form.
   * - **Store-and-forward buffering**
     - Every reading is written to a PSRAM buffer first and published from
       there, so a network outage costs no data until the buffer wraps.
   * - **Per-register diagnostics**
     - Each published reading carries its own success flag and, on failure,
       the Modbus error that caused it — see :ref:`diagnostics`.
   * - **Web configuration UI**
     - Full browser-based setup — no app or additional software required.
   * - **Over-the-Air updates**
     - Firmware and web UI updated wirelessly through the browser interface,
       with the configuration preserved across the update.


System Architecture
===================

The diagram below shows how ModBridge Pro sits between your Modbus devices
and the cloud::

                    RS-485 / Modbus TCP
   ┌─────────────┐                        ┌──────────────────────┐
   │ Modbus Dev 1│ ──────────────────────▶│                      │
   ├─────────────┤                        │    ModBridge Pro     │──▶ MQTT Broker
   │ Modbus Dev 2│ ──────────────────────▶│                      │
   ├─────────────┤                        │  Wi-Fi / Ethernet    │──▶ Google Sheets
   │ Modbus Dev 3│ ──────────────────────▶│                      │
   └─────────────┘                        └──────────────────────┘

Internally the work is split across both CPU cores.  Core 0 polls Modbus and
stages the readings; Core 1 owns the network — connection management, the
PSRAM buffer, cloud publishing and time sync.  A slow or failing cloud
connection therefore cannot stall Modbus polling.


Device Information
==================

.. list-table::
   :widths: 30 70
   :header-rows: 0

   * - **Firmware version**
     - v5.0.0
   * - **Time zone**
     - IST (UTC +5:30), synchronised from ``pool.ntp.org`` at boot and every
       hour thereafter
   * - **Poll / publish cadence**
     - One Modbus poll cycle per configured **Update Interval**


Document Conventions
====================

.. list-table::
   :widths: 20 80
   :header-rows: 0

   * - ``code``
     - File names, terminal commands, JSON keys.
   * - **Bold**
     - UI element names (tab labels, buttons, field names).
   * - *Italic*
     - Tab names when referring to the web configuration interface.
   * - .. note:: Note
     - Helpful background information.
   * - .. warning:: Warning
     - Actions that could cause data loss or misconfiguration.
   * - .. danger:: Danger
     - Potentially irreversible actions (factory reset, incompatible firmware).
